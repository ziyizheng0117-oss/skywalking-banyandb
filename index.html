1. 总体结论

已有雏形

BanyanDB 仓库已经有一套 MCP Prompt Generator + Query Executor 的 AI 生成 BYDBQL 方案，主要位于 mcp/。

不是内置 LLM

当前实现不是 BanyanDB server 直接调用 LLM，而是通过 MCP 暴露 prompt 和工具，由外部 MCP 客户端/LLM 生成 BYDBQL。

核心瓶颈

当前上下文主要包含 group/resource/index rule，缺少细粒度 tag/field/type/analyzer 信息和自动修复闭环。

自然语言描述
  ↓

  ↓
加载 BanyanDB groups/resources/index rules
  ↓
LLM 输出 JSON { "BydbQL": "SELECT ..." }
  ↓
list_resources_bydbql 执行查询
  ↓
BanyanDB BydbQL parser + transformer + native query service

2. BYDBQL 语法能力

BYDBQL 是 BanyanDB 自己的 SQL-like 查询 DSL，支持多种数据模型：

STREAMMEASURETRACEPROPERTYTOPN

SELECT * FROM STREAM sw IN default TIME > '-30m'

SELECT region, SUM(latency)
FROM MEASURE metrics IN default
TIME > '-1h'
GROUP BY region

SELECT trace_id
FROM TRACE sw_trace IN group1
TIME > '-30m'
WHERE service_id = 'payment-service'

SHOW TOP 10
FROM MEASURE service_latency IN default
TIME > '-30m'
ORDER BY DESC
  • Parser 使用 github.com/alecthomas/participle/v2，不是 ANTLR。
  • 语法入口是 Grammar.Select 或 Grammar.TopN。
  • WHERE 支持 AND/OR/括号优先级、比较、IN/NOT IN、HAVING/NOT HAVING、MATCH(...)。
  • TIME 支持比较和 BETWEEN，时间值支持 RFC3339、now、相对时长如 -30m/-1d。
  • Measure 支持聚合、GROUP BY、Top projection；TopN 采用 SHOW TOP N FROM MEASURE ...。
注意：文档声明 Stream/Measure/Trace/TopN 查询需要 TIME，但 grammar 中 Time 是可选字段。这意味着“文档约束”强于“语法约束”，生产级 AI 生成器应按文档约束补 TIME。

  ↓

  ↓
streamv1.QueryRequest / measurev1.QueryRequest / tracev1.QueryRequest / propertyv1.QueryRequest / measurev1.TopNRequest
  ↓
streamSvc.Query / measureSvc.Query / traceSvc.Query / propertyServer.Query / measureSvc.TopN

Transformer 会结合 metadata repo 拉取 schema，做 tag/field/projection/criteria/time/order/aggregation 的语义转换。因此 AI 生成 BYDBQL 的关键不是“写得像 SQL”，而是要贴合 BanyanDB schema。

4. 当前 AI 生成方案：MCP Prompt Generator

核心文件：

  • mcp/src/query/llm-prompt.ts：生成完整 LLM prompt。
  • mcp/src/query/context.ts：加载 groups/resources/index rules。
  • mcp/src/query/validation.ts：校验输入和 BYDBQL 只读安全边界。
  • mcp/src/server/mcp.ts：注册 MCP tools 和 prompt。

Prompt 注入的信息

上下文来源用途
GroupsbanyandbClient.listGroups()帮助选择 IN group
Resource → Group MappinglistStreams/listMeasures/listTraces/listProperties/listTopN用户只说资源名时，推断资源类型和 group
Indexed FieldslistIndexRule(group) 且 !noSort约束 ORDER BY 只能使用可排序索引字段

Prompt 里的关键规则

  • 区分 last N time units 和 last N data points：last 3 days 是 TIME，不是 LIMIT。
  • 只有明确请求排序/条数时才添加 ORDER BY/LIMIT。
  • TOPN 只针对 MEASURE 的 ranking 语义，格式为 SHOW TOP N FROM MEASURE ...。
  • ORDER BY 字段必须在 indexed fields 中；不匹配时做相似字段替换或省略。
  • 输出 JSON，至少包含 BydbQL 字段。

5. 校验与安全边界

mcp/src/query/validation.ts 做了基础安全限制：

  • BydbQL 长度上限 4096，description 上限 2048。
  • 只允许 SELECT 或 SHOW TOP 开头。
  • 禁止 ;、--、/*、*/，减少多语句和注释注入风险。
  • resource_type/resource_name/group 有白名单和 identifier pattern 校验。
MCP 参数校验
  ↓
只读前缀校验 SELECT / SHOW TOP
  ↓
禁止多语句/comment token
  ↓
BanyanDB ParseQuery 语法校验
  ↓
Transformer 结合 schema 做语义校验
  ↓
执行原生查询

6. 当前方案缺口

  1. 没有自动 parse/transform dry-run：LLM 输出后通常到执行阶段才暴露错误。
  2. schema context 不够细：当前多是资源名和 index rule，缺 tag families、fields、类型、analyzer、是否可 MATCH/aggregate。
  3. 没有错误驱动自修复：执行失败后没有把 parser/transformer 错误自动反馈给 LLM 重写。
  4. 没有 explain/validate API：AI 无法低成本验证 query 会转成什么 native request。
  5. Prompt 单体较长：后续可拆成 system rules、grammar summary、schema context、few-shot、output schema。

7. 生产级 NL → BYDBQL Agent 建议架构

用户自然语言
  ↓
Intent Parser / Query Planner
  ↓
Schema Retriever（groups/resources/tags/fields/index/analyzer）
  ↓
LLM Generate BydbQL JSON
  ↓
Static Validator
  ↓
BanyanDB Parse/Transform Dry Run 或 Explain
  ↓
Auto Repair Loop（最多 2-3 次）
  ↓
Execute Query
  ↓
Result Summarizer

建议新增能力

  • POST /v1/bydbql/validate：只 parse + transform，不扫数据。
  • POST /v1/bydbql/explain：返回 query type、native request、warnings。
  • Schema Retriever 返回字段级上下文：tag/field/type/index/analyzer/aggregatable/matchable。
  • Validator 规则化：TIME 必填策略、ORDER BY 索引校验、GROUP BY 字段存在、aggregation 字段类型校验。
  • Repair loop：把错误信息、原 query、可用 schema 传回 LLM，只允许修正 JSON。
