# BanyanDB QL Plugin for Claude Code

You have access to a BanyanDB MCP server (`banyandb`) that lets you discover schemas, generate BydbQL queries, and execute them against a live BanyanDB instance. Use these capabilities proactively whenever the user's request involves BanyanDB data, observability metrics, traces, logs, or service health.

## MCP Tools Available

- **`list_groups_schemas`** — Discover available groups and resources (streams, measures, traces, properties).
- **`get_generate_bydbql_prompt`** — Get a schema-aware prompt for converting natural language to BydbQL. Returns indexed fields, resource-to-group mappings, and syntax rules.
- **`list_resources_bydbql`** — Execute a read-only BydbQL query and return results.

## Query Generation Workflow

When the user asks to query BanyanDB or asks a question answerable with BanyanDB data:

1. **Discover schema first.** Call `list_groups_schemas` with `resource_type="groups"` to see what exists.
2. **Drill into relevant groups.** List `streams`, `measures`, `traces`, or `properties` for groups that match the user's intent.
3. **Generate BydbQL.** Call `get_generate_bydbql_prompt` with the user's natural language description. Parse the returned JSON to extract the `BydbQL` field.
4. **Execute.** Call `list_resources_bydbql` with the generated BydbQL.
5. **Present results.** Show the BydbQL used, a concise summary of results, and any caveats (empty results, time range assumptions, etc.).

If the user provides BydbQL directly, execute it immediately — only discover schemas if execution fails.

## BydbQL Quick Reference

```
SELECT fields FROM RESOURCE_TYPE resource_name IN group_name [TIME clause] [AGGREGATE BY clause] [ORDER BY field [ASC|DESC]] [LIMIT N]

SHOW TOP N FROM MEASURE measure_name IN group_name TIME time_condition [AGGREGATE BY agg_function] [ORDER BY DESC|ASC]
```

Resource types: `STREAM`, `MEASURE`, `TRACE`, `PROPERTY`, `TOPN`

Time syntax: `TIME >= '-1h'`, `TIME > '-1d'`, `TIME BETWEEN '-24h' AND '-1h'`

Critical rules:
- ORDER BY can **only** use indexed fields. Always validate against live schema.
- LIMIT must come **after** ORDER BY.
- Clause order: TIME → AGGREGATE BY → ORDER BY → LIMIT.
- "last 3 days" = `TIME > '-3d'` (time range, no LIMIT). "last 30 spans" = `ORDER BY ... LIMIT 30` (data points).

## Symptom Analysis Workflow

When the user describes a problem or phenomenon (not a direct query):

1. **Extract signals**: service names, trace IDs, endpoints, error text, time window, expected vs actual behavior.
2. **Default time window**: If not specified, use last 30 minutes and state that assumption.
3. **Discover available data**: List groups and relevant resources.
4. **Generate focused queries**: Prefer time-bounded, narrow-filter queries. Query across multiple resource types (measures for metrics, streams for logs, traces for spans) to correlate.
5. **Analyze and report**: What was queried, what changed or failed, likely root cause, confidence level, and next steps.

## Safety Rules

- Never invent group, resource, tag, or field names — always discover from live schema.
- Only execute read-only SELECT or SHOW TOP queries.
- Keep queries bounded by time or LIMIT.
- If BanyanDB is unreachable, tell the user to check:
  - MCP server is built: `cd mcp && npm install && npm run build`
  - BanyanDB is running at the configured address (default `localhost:17900`)
  - Set `BANYANDB_ADDRESS` for a remote instance.

## Environment

- Default BanyanDB address: `localhost:17900` (override via `BANYANDB_ADDRESS`)
- MCP entrypoint: `mcp/dist/index.js` (override via `BANYANDB_MCP_ENTRYPOINT`)
- If the plugin is outside the repository, set `SKYWALKING_BANYANDB_HOME` to the repo root.
